# MDE 마라토너식 개발 운영 STEP v1.0

## 적용 기준

이 STEP은 「MDE 마라토너식 개발 운영 지침 v1.0」을 실제 MDE 개발 과정에 적용하기 위한 운영 단계이다.

최우선 원칙은 다음과 같다.

- 기존 MDE Constitution과 Governance를 우선한다.
- 요구사항 → 최소 설계 → 구현 → 검증 → 문서 보완 → 지식 축적 순서를 유지한다.
- 기존 검증 완료 코드의 재사용을 최우선으로 한다.
- 검증되지 않은 기능 위에 다음 기능을 계속 추가하지 않는다.
- 신규 클래스·함수·파일·Framework는 실제 필요성이 확인된 경우에만 추가한다.
- STEP 완료는 코드 작성 여부가 아니라 실행과 검증 결과로 판단한다.
- 실패가 반복되면 기능 확장보다 오류 원인 제거를 우선한다.
- 실제 검증된 해결 경험만 지식 자산으로 승격한다.

# STEP MDE-M1 — STEP 완료 기록 표준화

## 1. 변경사항

새 기능을 구현하지 않는다.

현재 MDE 개발 과정의 각 STEP에 다음 완료 기록을 적용한다.

- STEP 번호 및 기능명
- 변경사항
- 기존 코드 재사용 내역
- 신규 코드가 필요한 이유
- 실행 방법
- 검증 결과
- 기존 기능 영향
- 미해결 문제
- 다음 STEP

기존 Constitution, Governance, Workflow, CLI 동작은 수정하지 않는다.

## 2. 기존 기능 재사용

현재 사용 중인:

- 기존 STEP 개발 기록
- Git 변경이력
- 테스트 결과
- Workflow 실행 결과

를 그대로 활용한다.

별도의 대형 문서관리 Framework는 만들지 않는다.

## 3. 신규 기능

필요한 것은 STEP 완료 기록 형식뿐이다.

예:

```text
STEP: MDE-XXX
기능명:
변경사항:
재사용 코드:
신규 코드 필요성:
실행:
검증:
기존 기능 영향:
미해결:
다음 STEP:
```

## 4. 실행

기존 개발 STEP 하나를 완료한 후 위 형식으로 기록한다.

## 5. 성공 결과

다음 조건을 모두 만족하면 완료한다.

1. 코드 변경사항을 확인할 수 있다.
2. 실제 실행 방법이 기록되어 있다.
3. 성공/실패 검증 결과가 기록되어 있다.
4. 미해결 문제가 숨겨지지 않는다.
5. 다음 STEP이 명확하다.

## 6. 이번 STEP에서 하지 않는 것

- 자동 기록 시스템
- 별도 DB
- 대시보드
- AI 평가
- Agent 자동 판단

은 구현하지 않는다.

## 7. 다음 STEP

STEP MDE-M2 — 구현 STEP과 검증 STEP 분리

# STEP MDE-M2 — 구현 STEP / 검증 STEP 분리

## 1. 변경사항

하루 1~2 STEP 운영을 다음 두 역할로 구분한다.

```text
STEP A
요구사항 확인
↓
최소 설계
↓
기능 구현

STEP B
실행
↓
검증
↓
회귀 확인
↓
완료 판정
```

한 STEP 안에서 구현과 검증이 가능한 작은 기능은 기존 방식대로 한 STEP으로 유지할 수 있다.

## 2. 기존 기능 재사용

현재 CLI, Test, Workflow 명령을 그대로 사용한다.

검증만을 위해 기존 기능을 재작성하지 않는다.

## 3. 신규 기능

신규 코드 없음.

운영 규칙만 적용한다.

## 4. 실행

예:

```text
MDE-21A
Workflow Retry 최소 구현

MDE-21B
Workflow Retry 실행 및 검증
```

## 5. 성공 결과

- A 단계 결과가 존재한다.
- B 단계에서 실제 실행된다.
- 실패하면 다음 기능으로 넘어가지 않는다.
- 검증 완료된 상태만 완료 처리한다.

## 6. 다음 STEP

STEP MDE-M3 — 실패 상태 보존

---

# STEP MDE-M3 — 실패 상태 보존

## 1. 변경사항

실패를 즉시 덮어쓰거나 계속 자동 재시도하지 않는다.

실패 시 최소한 다음 정보를 보존한다.

```text
STEP
Command
Stage
Result
Error
LastSuccessfulStage
RetryCount
```

기존 로그 또는 Workflow 결과에 이미 동일 정보가 존재한다면 새 저장소를 만들지 않는다.

## 2. 기존 기능 재사용

기존 MDE Workflow / Agent 로그를 우선 사용한다.

## 3. 신규 기능

기존 로그만으로 실패 위치를 구분할 수 없는 경우에만 최소 필드를 추가한다.

## 4. 동작 흐름

```text
실행
↓
실패
↓
오류 분류
↓
현재 상태 보존
↓
자동 재시도 제한
↓
원인 수정
↓
재검증
```

## 5. 성공 결과

같은 실패가 반복되었을 때:

- 어느 단계에서 실패했는지 확인 가능
- 마지막 성공 단계 확인 가능
- 미완료 변경과 정상 버전을 구분 가능

해야 한다.

## 6. 다음 STEP

STEP MDE-M4 — 회귀 검증 Gate

---

# STEP MDE-M4 — 검증 Gate

## 1. 변경사항

새 기능 완료 전에 최소 검증 Gate를 통과하도록 한다.

기본 흐름:

```text
새 기능 실행
↓
해당 기능 검증
↓
기존 핵심 기능 회귀 검증
↓
PASS
↓
Git 반영 가능
```

## 2. 기존 기능 재사용

현재 존재하는 test, ruff, workflow validation 등을 우선 사용한다.

새로운 테스트 Framework를 만들지 않는다.

## 3. 성공 결과

필수 검증 실패 시:

```text
SAVE / PUSH / RELEASE 보류
```

상태가 된다.

## 4. 다음 STEP

STEP MDE-M5 — 재사용 확인 Gate

---

# STEP MDE-M5 — 기존 코드 재사용 확인

## 1. 변경사항

신규 함수·클래스·모듈 생성 전에 다음 순서를 확인한다.

```text
기존 함수 존재?
↓
검증 완료?
↓
현재 기능에서 그대로 사용 가능?
↓
최소 확장으로 해결 가능?
↓
그래도 불가능할 때만 신규 코드
```

## 2. 신규 코드 생성 조건

다음 중 하나가 명확해야 한다.

- 기존 기능으로 해결 불가
- 책임이 명확히 다른 기능
- 기존 코드를 변경하면 회귀 위험이 더 큼
- 현재 STEP에 반드시 필요

## 3. 성공 결과

STEP 완료 기록에:

```text
재사용:
신규 생성:
신규 생성 이유:
```

가 남는다.

## 4. 다음 STEP

STEP MDE-M6 — Workflow 완주 측정

---

# STEP MDE-M6 — Workflow 완주 성공률 측정

## 1. 목표

개발 속도가 아니라 실제 완주율을 측정한다.

최소 측정값:

```text
WorkflowRunCount
WorkflowSuccessCount
WorkflowFailedCount
```

완주 성공률:

```text
WorkflowSuccessCount / WorkflowRunCount
```

## 2. 기존 기능 재사용

기존 Workflow 실행 결과에서 계산 가능하면 별도 저장하지 않는다.

## 3. 성공 결과

주간 단위로 최소 다음 내용을 알 수 있어야 한다.

- 실행 횟수
- 성공 횟수
- 실패 횟수
- 반복 실패 단계

## 4. 다음 STEP

STEP MDE-M7 — 재작업률 기록

---

# STEP MDE-M7 — 재작업률 측정

## 1. 목표

많이 구현했는지가 아니라 다시 고친 비율을 확인한다.

최초에는 복잡한 산식을 만들지 않는다.

예:

```text
완료 STEP       10
재작업 STEP      2
```

정도로 기록한다.

## 2. 활용

재작업이 늘어나면:

```text
기능 추가 속도 감소
↓
오류 유형 확인
↓
설계/검증 강화
```

로 전환한다.

## 3. 다음 STEP

STEP MDE-M8 — 검증 경험 Knowledge 승격

---

# STEP MDE-M8 — 검증 완료 경험만 Knowledge로 승격

## 1. 목표

AI가 제안했다는 이유만으로 MDE Knowledge에 넣지 않는다.

다음 과정을 통과한 해결책만 등록한다.

```text
문제 발생
↓
원인 확인
↓
수정
↓
실행 성공
↓
재검증
↓
재현 가능
↓
Knowledge 후보
```

## 2. Knowledge 최소 구조

기존 AutoKnowledge 또는 현재 MDE Knowledge 구조를 우선 재사용한다.

필요 정보 예:

```text
Problem
Cause
Solution
Validation
ApplicableContext
```

새로운 Knowledge DB는 만들지 않는다.

## 3. 성공 결과

동일 오류가 발생했을 때 과거 검증 해결책을 검색할 수 있다.

## 4. 다음 STEP

STEP MDE-M9 — 주간 Review

---

# STEP MDE-M9 — 주간 마라토너식 Review

## 1. 목표

일주일 개발 결과를 이전 주와 비교한다.

## 2. 확인 항목

- Workflow 완주 성공률
- 재작업률
- 신규 기능 수
- 검증 완료 STEP 수
- 실패가 반복된 단계
- 기존 코드 재사용 사례
- 자동화된 반복 작업
- 새로 축적된 검증 Knowledge

## 3. 판단

성과가 낮더라도 무조건 기능량을 늘리지 않는다.

```text
실패율 증가
→ 안정화

재작업 증가
→ 원인 분석

완주율 증가
→ 현재 방식 유지

반복 작업 증가
→ 자동화 후보 검토
```

## 4. 다음 STEP

STEP MDE-M10 — 반복 작업 자동화 후보 추출

# STEP MDE-M10 — 자동화 후보 발견

## 1. 목표

반복 실행되는 개발 작업 중 실제 자동화 가치가 확인된 것만 후보로 만든다.

예:

- 동일 검증 명령 반복
- 동일 파일 생성 반복
- 동일 오류 확인 반복
- 동일 Workflow 수동 연결 반복

## 2. 구현 원칙

자동화 후보가 발견되었다고 바로 Agent를 만들지 않는다.

```text
반복 확인
↓
수동 절차 안정화
↓
입력/출력 확정
↓
최소 자동화
↓
검증
```

## 3. 다음 STEP

STEP MDE-M11 — Agent 적용 후보 판단

---

# STEP MDE-M11 — Agent 적용 판단

## 1. 목표

Agent를 기술적으로 가능하다는 이유만으로 도입하지 않는다.

다음 조건을 만족하는 작업부터 검토한다.

- 절차가 반복된다.
- 입력과 출력이 명확하다.
- 실패 여부를 자동 판정할 수 있다.
- 기존 Workflow가 안정적이다.
- 실패 시 중단할 수 있다.

## 2. 초기 Agent 역할

초기에는 자율 설계보다 정해진 Workflow 실행 Agent를 우선한다.

```text
Task
↓
Known Workflow
↓
Execute
↓
Validate
↓
PASS / STOP
```

## 3. 하지 않는 것

- 무제한 자기수정
- 검증 없는 자동 Push
- 검증 없는 자동 Release
- 실패 상태에서 무한 재시도
- 기존 Governance 우회

## 4. 다음 STEP

STEP MDE-M12 — MDE 자기개선 Loop

# STEP MDE-M12 — 안전한 자기개선 Loop

## 1. 목표

MDE가 MDE 자신의 기능 개선을 보조할 수 있도록 한다.

최종 흐름:

```text
개선 요구
↓
관련 Knowledge 검색
↓
기존 코드 재사용 확인
↓
최소 변경안 생성
↓
코드 작성
↓
Test
↓
Workflow 검증
↓
회귀 검증
↓
개발자 승인
↓
Save / Push
↓
검증 경험 Knowledge 축적
```

## 2. 최종 승인

MDE가 자동화 범위를 확대하더라도 다음은 개발자가 담당한다.

- 목표
- 설계 방향
- 품질 기준
- 보안 판단
- 최종 승인

## 3. 완료 기준

MDE가 코드를 많이 작성하는 것이 아니라:

- 기존 자산을 재사용하고
- 실패 시 안전하게 중단하고
- 테스트를 수행하고
- 검증 결과를 남기고
- 승인된 결과만 반영하며
- 성공 경험을 다시 재사용

할 수 있을 때 자기개선 Loop가 완성된 것으로 본다.

↓

# 핵심 원칙

마라토너식 MDE 개발의 목표는 매일 최대량의 코드를 작성하는 것이 아니다.

```text
짧은 STEP
+
반복 가능한 실행
+
검증
+
회복
+
검증된 경험 축적
+
점진적 자동화
```

를 지속하여 장기적으로 MDE의 개발 품질과 자동화 수준을 높이는 것이다.

빠른 한 번의 개발보다 검증된 STEP을 계속 완주하는 구조를 우선한다.
