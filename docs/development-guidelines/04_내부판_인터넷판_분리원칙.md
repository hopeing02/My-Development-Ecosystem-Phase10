# **업무자동화 시스템 공공기관 내부판·인터넷판 분리 개발 원칙**

## **1\. 목적**

현재 개발하는 업무자동화 시스템은 공공기관 내부 업무에 사용되는 버전과, 향후 퇴직 후 별도로 개발할 수 있는 인터넷·범용 버전을 명확히 구분한다.

두 버전은 기능적 아이디어나 일반적인 설계 철학은 참고할 수 있지만, 기관 내부의 코드·데이터·업무규칙·문서·보안정보를 인터넷판으로 직접 이전하거나 복사하지 않는다.

기본 원칙은 다음과 같다.

**기관 내부판은 기관 업무용으로 개발하고, 인터넷판은 별도의 범용 제품으로 독립 구현한다.**

---

# **2\. 기관 내부판**

기관 내부판은 공공기관의 내부 업무자동화를 목적으로 한다.

포함 가능한 항목:

* 기관 업무 전용 기능  
* 기관 내부 Excel/VBA  
* 기관 내부 파일 구조  
* 기관 내부 업무명·화면명  
* 기관 내부 업무절차  
* 기관 내부 데이터 처리 규칙  
* 기관 전용 Adapter  
* 기관 전용 설정  
* 기관에서 승인한 배포본  
* 기관 업무에 필요한 로그 및 버전관리

기관 내부판에서는 다음 사항을 우선한다.

* 외부 인터넷 통신 최소화 또는 금지  
* 기관 보안정책 준수  
* 개인정보 및 민감정보 최소 저장  
* 허용된 파일과 경로만 접근  
* 관리자 권한 사용 최소화  
* 승인된 배포 절차 사용  
* 변경이력 기록  
* 공식 배포본과 사용자 수정본 분리

---

# **3\. 인터넷·범용판**

인터넷판은 기관 내부판을 그대로 외부에 공개하는 방식으로 만들지 않는다.

다음 원칙으로 새롭게 구현한다.

* 새로운 프로젝트로 생성  
* 새로운 소스코드 작성  
* 새로운 UI 작성  
* 새로운 제품명 사용 가능  
* 일반화된 업무자동화 기능만 구현  
* 특정 기관 업무에 종속되지 않는 구조 사용  
* 공개 또는 합법적으로 사용할 수 있는 데이터만 사용  
* 기관 내부 데이터 사용 금지  
* 기관 내부 문서 사용 금지  
* 기관 내부 소스코드 복사 금지  
* 기관 내부 접속정보 사용 금지  
* 기관 내부 파일 경로 사용 금지  
* 기관 내부 DB 구조 직접 복제 금지  
* 기관 보안 설정·계정·인증정보 사용 금지

인터넷판은 기관판의 복제품이 아니라 **별도의 범용 업무자동화 제품** 으로 취급한다.

---

# **4\. 공통으로 사용할 수 있는 영역**

다음과 같은 일반적인 소프트웨어 설계 개념은 범용화 후보로 볼 수 있다.

예:

* Entity  
* EntityRef  
* Relation  
* Version  
* Result  
* Repository  
* Service  
* Adapter  
* Parser  
* FileIndex 개념  
* 변경이력 관리 개념  
* Version Capture 개념  
* Diff 개념  
* API 기반 기능 호출  
* Local API 구조  
* 플러그인 구조  
* 확장 모듈 구조  
* WorkItem 개념  
* BusinessObject 개념  
* 검색·분류·태그 개념

단, 동일한 개념을 사용하더라도 기관 내부 코드를 복사하지 말고 인터넷판에서 새로 구현한다.

---

# **5\. 코드 재사용 원칙**

기관 내부판 내부에서는 다음 원칙을 따른다.

**검증 완료 코드는 재작성하지 않고 기존 코드를 우선 재사용한다.**

하지만 기관판과 인터넷판 사이에서는 이 원칙을 그대로 적용하지 않는다.

기관판 → 인터넷판 전환 시에는:

기관 코드 복사  
    X

기관의 일반적인 설계 개념 분석  
    ↓  
범용 요구사항으로 재정의  
    ↓  
새 인터페이스 설계  
    ↓  
새 코드 구현

방식을 사용한다.

---

# **6\. 핵심 Core 분리 원칙**

시스템은 가능하면 다음 구조를 따른다.

UI  
↓  
Controller  
↓  
Service  
↓  
Core  
↓  
Repository / Adapter  
↓  
Storage 또는 외부 시스템

기관 전용 기능은 Core에 직접 섞지 않고 Adapter 또는 기관 전용 Service에 둔다.

예:

범용 Core  
├─ File  
├─ Search  
├─ Relation  
├─ Version  
├─ Diff  
└─ Automation

기관 Adapter  
├─ 기관 파일 구조  
├─ 기관 Excel  
├─ 기관 업무규칙  
└─ 기관 내부 시스템 연결

이렇게 하여 범용 개념과 기관 전용 기능을 논리적으로 분리한다.

단, 현재 시스템이 이미 구현되어 있는 경우에는 이 원칙을 적용하기 위해 기존 검증 완료 코드를 대규모 리팩터링하지 않는다.

새로운 기능부터 점진적으로 적용한다.

---

# **7\. API 원칙**

향후 사용자 확장 기능은 가능하면 Core를 직접 수정하는 대신 API를 통해 사용하게 한다.

구조:

사용자 프로그램  
Excel / VBA / Python / HTML  
        ↓  
       API  
        ↓  
보안 및 입력 검증  
        ↓  
      Core

API에서는 다음 항목을 통제한다.

* 사용자 권한  
* 입력값 검증  
* 허용 경로  
* 사용 가능한 기능  
* 외부 통신 여부  
* 로그 기록 범위

Core 내부 구현은 사용자에게 직접 노출하지 않는 방향을 우선한다.

---

# **8\. 사용자 참여 개발**

사용자가 업무자동화 개발에 참여하는 것은 허용할 수 있다.

다만 사용자가 공식 Core를 직접 수정하는 방식은 피한다.

권장 구조:

Official Core  
      ↓  
Public API  
      ↓  
User Extension

사용자는 API를 조합하여 자신의 자동화를 만든다.

좋은 사용자 기능은 다음 절차로 공식 기능 후보가 될 수 있다.

사용자 개발  
↓  
제안  
↓  
코드/기능 검토  
↓  
보안 검토  
↓  
테스트  
↓  
공식판 반영  
---

# **9\. 보안 기본 원칙**

기관 내부판에는 최소한 다음 보안 원칙을 적용한다.

1. 외부 통신이 필요하지 않으면 구현하지 않는다.  
2. 관리자 권한을 기본 요구사항으로 하지 않는다.  
3. 입력값을 그대로 실행하거나 SQL·명령어로 연결하지 않는다.  
4. 파일 접근은 필요한 경로로 제한한다.  
5. 민감정보를 로그에 저장하지 않는다.  
6. 주민번호·계좌번호 등 개인정보는 필요하지 않으면 저장하지 않는다.  
7. 임시파일에 업무 원문이 남지 않도록 한다.  
8. 공식 배포본과 개인 수정본을 구분한다.  
9. 버전 정보를 기록한다.  
10. 사용자가 Core를 직접 수정하지 않도록 구조적으로 분리한다.  
11. Shell, PowerShell, 외부 EXE 실행 등은 필요성이 확인된 경우에만 사용한다.  
12. 네트워크 전체 탐색이나 불필요한 폴더 검색을 하지 않는다.

---

# **10\. 개발 방식**

모든 개발은 다음 순서를 따른다.

최소 구현  
↓  
실행  
↓  
검증  
↓  
실제 사용  
↓  
문제 확인  
↓  
필요한 부분만 개선  
↓  
다음 기능 추가

초기 단계에서 미래 기능을 예상하여 과도한 Framework를 만들지 않는다.

신규 함수는 해당 STEP에 반드시 필요한 경우에만 추가한다.

기존 검증 완료 코드는 가능한 한 그대로 재사용한다.

---

# **11\. 기관판과 인터넷판의 경계 확인**

새로운 기능을 개발할 때 항상 먼저 다음을 판단한다.

### **A. 기관 전용 기능인가?**

다음 중 하나라도 해당하면 기관 전용으로 본다.

* 특정 기관 업무명 사용  
* 특정 기관 데이터 사용  
* 특정 기관 파일 형식에 종속  
* 특정 기관 내부 시스템 연계  
* 특정 기관 직원·조직 정보 사용  
* 기관 내부 보안정보 사용  
* 기관 내부 업무절차를 구현

이 경우 기관판에만 구현한다.

### **B. 일반적인 기능인가?**

예:

* 파일 검색  
* 버전 비교  
* 관계 관리  
* 변경이력  
* 문서 분류  
* 태그  
* 일반적인 데이터 변환  
* 일반적인 자동화 Workflow

이 경우 향후 범용판 후보로 기록할 수 있다.

---

# **12\. 인터넷판 개발 시 금지사항**

인터넷판을 만들 때 다음은 사용하지 않는다.

* 기관 내부 소스코드  
* 기관 데이터  
* 기관 내부 화면 캡처  
* 기관 파일 샘플  
* 기관 계정정보  
* 기관 접속 주소  
* 기관 업무 매뉴얼 원문  
* 내부 문서  
* 개인정보  
* 내부 보안설정  
* 비밀정보  
* 공개가 허용되지 않은 업무규칙

필요한 경우 인터넷판 테스트 데이터는 별도로 생성한다.

---

# **13\. 퇴직을 고려한 설계**

기관판은 개발자가 퇴직하더라도 기관에서 운영할 수 있도록 한다.

최소한 다음을 남길 수 있는 구조로 개발한다.

* 소스 위치  
* 버전  
* 주요 모듈 설명  
* 실행 방법  
* 배포 방법  
* 설정 방법  
* 보안 설정  
* 오류 확인 방법  
* 변경이력  
* 운영 담당자가 알아야 할 최소 문서

그러나 범용 인터넷판과 기관판의 경계는 명확하게 유지한다.

---

# **14\. AI에게 코드 작성을 요청할 때 적용할 규칙**

코드를 작성하기 전에 다음을 먼저 확인한다.

1. 기존 검증 완료 함수로 해결할 수 있는가?  
2. 기관 전용 기능인가, 범용 기능인가?  
3. 새로운 함수가 정말 필요한가?  
4. Core 변경 없이 Adapter 또는 Service 추가로 가능한가?  
5. 기관 데이터나 내부정보가 인터넷판 코드에 섞이지 않는가?  
6. 보안상 불필요한 권한이나 외부통신이 추가되지 않는가?

기존 함수로 해결할 수 있으면 새로운 함수를 만들지 않는다.

기관 전용 로직은 범용 Core에 넣지 않는다.

기존 검증 완료 코드를 구조 개선만을 목적으로 재작성하지 않는다.

---

# **15\. 최종 목표**

장기적으로 다음 구조를 목표로 한다.

              범용 업무자동화 개념  
                       │  
              ┌────────┴────────┐  
              │                 │  
        공공기관 내부판        인터넷 범용판  
              │                 │  
     기관 전용 Adapter       범용 Adapter  
     기관 전용 업무규칙       일반 Workflow  
     내부 보안정책            인터넷 서비스  
              │                 │  
         내부 사용자          일반 사용자

두 제품은 서로 영향을 줄 수 있는 아이디어와 설계 경험은 공유할 수 있지만, 코드·데이터·기관 내부정보는 명확하게 분리한다.

최우선 원칙은 다음 세 가지이다.

**① 기관 내부정보를 외부 제품으로 가져가지 않는다.**

**② 기관판과 인터넷판의 소스코드를 별도로 관리한다.**

**③ 범용화할 기능은 개념과 요구사항을 다시 정의한 후 새 코드로 구현한다.**

**신규 기능을 설계할 때 기존 기술과 다른 처리 방식, 데이터 연결 방식, 자동화 순서 또는 기술적 효과가 있는지 확인한다. 특허 가능성이 있다고 판단되는 기능은 일반 기능과 분리하여 `PatentCandidate`로 기록하고, 외부 공개·인터넷판 배포 전에 직무발명 및 권리귀속 여부를 확인한다.**
