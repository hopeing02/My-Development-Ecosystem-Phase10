# **VBA 상용화·복제방지·라이선스 설계 공통 프롬프트**

## **1\. 목표**

완성된 Excel/VBA 프로그램을 상용 제품으로 판매할 때 다음 목표를 동시에 만족하도록 설계한다.

1. 사용자가 프로그램 파일을 다른 사람에게 복사하여 무단 사용하는 것을 최대한 어렵게 한다.  
2. 핵심 소스코드와 핵심 알고리즘이 쉽게 노출되지 않도록 한다.  
3. 사용자가 프로그램의 동작 원리와 결과를 충분히 이해할 수 있도록 한다.  
4. 과도한 SaaS 구조를 만들지 않는다.  
5. 개발자가 장기간 서버 운영에 종속되지 않도록 한다.  
6. 개인정보 및 회원정보 수집을 최소화한다.  
7. 서비스 종료 이후에도 정품 구매자의 프로그램 사용권을 보호할 수 있도록 한다.  
8. 보안 때문에 프로그램의 사용성이 지나치게 나빠지지 않도록 한다.

---

# **2\. 기본 제품 구조**

초기 상용판은 완전한 SaaS가 아니라 다음 구조를 우선한다.

사용자 PC

Excel/VBA 프로그램  
↓  
로컬 기능 실행  
↓  
필요할 때만 License API 호출  
↓  
라이선스 서버

기본 원칙:

* 대부분의 업무 기능은 사용자 PC에서 실행한다.  
* 서버는 주로 라이선스 인증을 담당한다.  
* 매 실행마다 서버 접속을 강제하지 않는다.  
* 한 번 정상 인증된 사용자는 일정 기간 오프라인 사용을 허용한다.  
* SaaS 전환은 실제 필요성이 확인된 이후에만 검토한다.

초기 목표 구조는 대략 다음과 같이 한다.

로컬 기능 80\~90%  
온라인 기능 10\~20%

단, 이 비율을 기계적으로 적용하지 말고 보호 가치가 높은 기능을 기준으로 판단한다.

---

# **3\. 무단 복제 방지 원칙**

단순히 Excel 파일에 암호만 설정하는 방식에 의존하지 않는다.

다음 보호 장치를 조합한다.

LicenseId  
\+  
LicenseKey  
\+  
DeviceId  
\+  
허용 PC 수  
\+  
라이선스 상태  
\+  
서명된 라이선스 정보

예:

LicenseId  
ProductId  
LicenseKeyHash  
DeviceIdHash  
MaxDevices  
Status  
ExpiresAt  
LastVerifiedAt

LicenseKey와 DeviceId는 가능하면 서버에서 원문 그대로 저장하지 않고 적절한 해시 또는 안전한 식별 방식 사용을 검토한다.

사용자가 프로그램 파일을 다른 사람에게 복사해도 등록되지 않은 PC에서는 정상적인 라이선스 인증 없이는 사용할 수 없도록 한다.

---

# **4\. 개인정보 최소화 원칙**

라이선스 인증을 위해 불필요한 개인정보를 수집하지 않는다.

가급적 다음 정보는 라이선스 서버에 저장하지 않는다.

* 주민등록번호  
* 상세 주소  
* 전화번호  
* 생년월일  
* 카드번호  
* 불필요한 사용자 프로필

가능하면 회원가입 없이 다음 정보만으로 라이선스를 관리할 수 있도록 설계한다.

LicenseId  
LicenseKeyHash  
ProductId  
DeviceIdHash  
MaxDevices  
Status  
ExpiresAt  
LastVerifiedAt

결제가 필요한 경우 결제정보는 직접 저장하지 않고 PG사 등 외부 결제 서비스를 활용하고 내부 시스템에는 최소한의 결제 결과 또는 주문 식별값만 저장하는 구조를 우선한다.

---

# **5\. 클라이언트에 비밀정보 저장 금지**

VBA 파일은 사용자가 직접 보유하는 프로그램이므로 다음 정보를 VBA 코드 내부에 저장하지 않는다.

* 서버 관리자 비밀번호  
* 서버 비밀키  
* 관리자 API Key  
* DB 접속 비밀번호  
* 라이선스 생성용 개인키  
* 핵심 보안 토큰

VBA에는 노출되어도 치명적이지 않은 정보만 둔다.

가능하다면 서버에서 라이선스를 서명하고 클라이언트에서는 공개키 등을 이용하여 검증하는 구조를 검토한다.

---

# **6\. 로직 공개 수준 구분**

사용자가 프로그램을 잘 사용하려면 프로그램의 동작 원리를 설명해야 한다.

그러나 동작 원리 설명과 핵심 구현 로직 공개를 구분한다.

사용자에게 공개해야 하는 내용:

* 어떤 데이터를 입력하는가  
* 어떤 기준으로 결과가 만들어지는가  
* 결과가 의미하는 것은 무엇인가  
* 특정 결과가 나온 주요 이유  
* 프로그램의 한계  
* 잘못된 결과가 발생할 수 있는 조건  
* 결과 수정 방법  
* 사용자에게 필요한 업무 절차

공개하지 않아도 되는 내용:

* 정확한 점수 계산식  
* 세부 가중치  
* 내부 임계값  
* 내부 DB Schema 전체  
* 세부 데이터 정규화 방식  
* 후보 생성 알고리즘  
* 내부 추천 순위 계산식  
* 예외처리 알고리즘  
* 핵심 소스코드  
* 서버 내부 처리 순서  
* 내부 프롬프트  
* 독자적인 분석 알고리즘

사용설명서는 사용자가 충분히 활용할 수 있도록 자세히 작성하되, 프로그램을 그대로 재구현할 수 있는 수준의 내부 알고리즘 설명은 피한다.

---

# **7\. 설명 가능한 결과 제공**

핵심 계산식을 공개하는 대신 결과의 근거를 사용자에게 제공한다.

예:

추천 업무

* 동일 업무대상과 연결됨  
* 최근 관련 파일을 사용함  
* 유사 업무가 존재함  
* 관련 자료가 여러 건 연결되어 있음

또는

분석 결과

* 변경된 프로시저 발견  
* 관련 호출 함수 존재  
* 연결된 BusinessObject 존재  
* 최근 버전과 차이가 있음

즉,

결과  
\+  
Evidence  
\+  
설명

구조를 기본으로 한다.

내부 계산 공식은 보호하면서도 사용자가 프로그램을 신뢰하고 이해할 수 있도록 한다.

---

# **8\. 핵심 로직 보호 기준**

모든 기능을 서버로 이전하지 않는다.

기능마다 다음 기준으로 분류한다.

A. 공개되어도 문제가 거의 없는 기능

* Excel 화면  
* 일반 입력  
* 검색 화면  
* 파일 선택  
* 단순 정렬  
* 기본 보고서 생성

→ 로컬 VBA에 유지 가능

B. 일부 보호가 필요한 기능

* 데이터 정규화  
* 복잡한 매칭  
* 특정 업무 규칙  
* 유사도 계산

→ 로컬 보호 또는 서버 이전 검토

C. 핵심 경쟁력에 해당하는 기능

* 독자 추천 알고리즘  
* 고유 분석 알고리즘  
* 자체 점수 계산  
* 중요한 관계 추론  
* 고유 자동화 판단 규칙  
* 제품 성능을 결정하는 핵심 로직

→ API 또는 보호된 서버 영역 배치를 우선 검토

기능 하나를 서버로 옮길 때마다 반드시 다음을 검토한다.

1. 실제로 보호할 가치가 있는가?  
2. 서버가 중단되면 제품 전체가 멈추는가?  
3. 오프라인 업무가 가능한가?  
4. 유지보수 부담이 얼마나 증가하는가?  
5. 서버 이전으로 얻는 보안 효과가 충분한가?

---

# **9\. AI에 의한 모방 가능성 대응**

AI를 이용하면 사용설명서와 화면을 보고 유사한 프로그램을 만드는 것이 가능하다는 점을 전제로 한다.

따라서 목표를

"누구도 비슷한 프로그램을 만들 수 없게 한다"

가 아니라

"비슷한 화면을 만들어도 핵심 성능과 품질을 쉽게 재현하지 못하게 한다"

로 설정한다.

경쟁력이 다음 요소에 축적되도록 한다.

* 독자적인 데이터 구조  
* 실제 업무 규칙  
* 관계 데이터  
* 분석 이력  
* 사용자 피드백  
* Evidence 축적  
* 버전 이력  
* 자체 알고리즘  
* 예외처리 노하우  
* 지속적인 기능 개선

UI만 복제해서 동일한 품질을 내기 어렵게 만드는 것이 목표다.

---

# **10\. 온라인 인증 방식**

프로그램 실행 때마다 반드시 서버 인증을 요구하지 않는다.

예:

최초 실행  
→ 온라인 라이선스 인증  
→ 서명된 인증정보 로컬 저장

이후 실행  
→ 로컬 인증정보 검증  
→ 정상 실행

일정 기간 경과  
→ 서버 재인증

예를 들어 7일, 14일, 30일 등의 재인증 주기를 사용할 수 있다.

재인증 기간은 제품 특성과 고객 환경을 고려하여 결정한다.

인터넷 장애 또는 인증 서버의 일시 장애 때문에 정품 사용자의 프로그램이 바로 중단되지 않도록 Grace Period 구조를 고려한다.

---

# **11\. 서비스 종료 대비**

개발자가 평생 서버를 유지해야만 프로그램이 작동하는 구조를 만들지 않는다.

서비스를 종료해야 할 상황에 대비하여 다음 구조를 설계한다.

정상 운영 기간  
→ 온라인 인증

서비스 종료 결정  
→ 기존 정품 구매자 확인

정품 구매자  
→ 영구 오프라인 라이선스 또는 장기 라이선스 발급

그 이후  
→ 인증 서버 종료 가능

서비스 종료 이후에도 기존 정품 사용자가 합리적인 범위에서 구매한 프로그램을 계속 사용할 수 있도록 한다.

---

# **12\. 라이선스 유형**

초기에는 복잡한 요금제를 만들지 않는다.

예:

개인용

* 사용자 1명  
* PC 1\~2대

기업용

* 지정 사용자 또는 지정 PC 수  
* 필요 시 별도 계약

영구 라이선스

* 프로그램 버전 기준 영구 사용  
* 업데이트 정책 별도

구독 라이선스

* 필요성이 확인된 경우에만 도입

처음부터 복잡한 Free / Basic / Standard / Professional / Enterprise 요금체계를 만들지 않는다.

---

# **13\. VBA 코드 보호**

VBA 프로젝트 암호만으로 코드 보호가 완벽하다고 가정하지 않는다.

VBA 코드 보호 기능은 보조적인 보호 수단으로만 사용한다.

중요 로직이 VBA 내부에 있어야 하는 경우에는 다음을 함께 고려한다.

* 모듈 책임 분리  
* 핵심 계산 코드 최소 노출  
* 불필요한 업무규칙 하드코딩 금지  
* 중요 설정값 외부 분리  
* 원본 소스 별도 보관  
* 배포본과 개발본 분리  
* 디지털 서명  
* 버전 관리  
* 변경 이력 관리

보안을 이유로 지나친 난독화를 적용하여 유지보수가 불가능해지는 구조는 피한다.

---

# **14\. 제품 소스 분리**

기관 내부판과 일반 상용 인터넷판은 별도 제품으로 관리한다.

기관 내부판의 다음 항목을 인터넷판으로 직접 복사하지 않는다.

* 기관 업무 데이터  
* 기관 전용 업무규칙  
* 기관 내부 코드  
* 기관 문서  
* 보안정보  
* 기관 전용 파일구조  
* 기관 전용 Adapter 및 설정값

공통으로 사용할 수 있는 것은 검증된 일반적인 설계 아이디어와 범용 알고리즘으로 한정한다.

상용판은 별도의 Repository와 별도의 소스코드로 관리한다.

---

# **15\. 특허·저작권·영업비밀 구분**

제품 보호를 기술적 복제방지 하나에만 의존하지 않는다.

다음 세 가지를 구분하여 검토한다.

저작권  
→ 작성한 프로그램 코드, 문서, 화면 구성 등의 보호

영업비밀  
→ 공개하지 않는 알고리즘, 가중치, 내부 규칙, 운영 노하우

특허  
→ 신규성과 진보성이 있을 가능성이 있는 기술적 방법 또는 시스템

특허 가능성이 있다고 판단되는 핵심 기능은 공개 문서나 판매 설명서에 세부 알고리즘을 공개하기 전에 별도로 검토한다.

---

# **16\. 개발 원칙**

상용화 보안 기능 역시 기존 개발 원칙을 따른다.

최소 구현  
→ 실행  
→ 검증  
→ 점진 확장

처음부터 거대한 SaaS, 회원관리시스템, 복잡한 결제시스템을 만들지 않는다.

초기 구현 순서는 다음을 기본으로 한다.

STEP 1  
LicenseId / LicenseKey 구조

STEP 2  
PC 또는 Device 등록

STEP 3  
허용 PC 수 제한

STEP 4  
서명된 로컬 라이선스

STEP 5  
경량 License API

STEP 6  
주기적 온라인 재인증

STEP 7  
서비스 종료용 영구 오프라인 라이선스

STEP 8  
필요한 핵심 기능만 API 분리

각 STEP이 실제로 필요하고 검증된 경우에만 다음 단계로 확장한다.

---

# **17\. 코드 작성 요청 시 규칙**

내가 특정 STEP 구현을 요청하면 다음 순서로 답한다.

1. 이번 STEP에서 변경되는 내용  
2. 기존 코드 중 재사용할 부분  
3. 새로 필요한 최소 기능  
4. 모듈 또는 구성요소  
5. 실제 운영 코드  
6. 실행 방법  
7. 정상 실행 결과  
8. 보안상 확인사항  
9. 다음 STEP

기존 검증 완료 코드는 가능하면 수정하지 않는다.

신규 함수는 반드시 필요한 경우에만 만든다.

불필요한 Framework, Class, DB Table, 설정파일, 공통모듈을 선제적으로 만들지 않는다.

테스트 전용 코드보다 실제 운영 코드를 우선한다.

---

# **18\. 설계 판단 기준**

어떤 보안기술을 추가할지 판단할 때 항상 다음 순서로 검토한다.

보호 대상의 가치  
→ 실제 공격 가능성  
→ 방어 효과  
→ 개발 복잡도  
→ 운영 부담  
→ 사용자 불편  
→ 장기 유지보수 비용

보안 수준을 최대화하는 것이 목표가 아니라,

"충분한 복제방지 \+ 낮은 운영 부담 \+ 좋은 사용성"

사이의 균형을 목표로 한다.

# **최종 원칙**

100% 복제 방지를 목표로 하지 않는다.

목표는 다음 세 가지다.

1. 단순 파일 복사만으로는 무단 사용하기 어렵게 한다.  
2. 경쟁자가 화면이나 설명서를 모방해도 핵심 성능까지 쉽게 재현할 수 없게 한다.  
3. 개발자가 장기간 과도한 서버 운영 부담을 떠안지 않는다.

따라서 기본 전략은

로컬 프로그램  
\+  
경량 라이선스 인증  
\+  
핵심 로직 선택적 보호  
\+  
설명 가능한 결과  
\+  
최소 개인정보  
\+  
서비스 종료 대비

구조로 설계한다.

이 프롬프트를 기준으로 현재 완성된 프로그램을 상용화하려고 한다.  
먼저 기능별로 `로컬 유지 / 보호 필요 / API 이전 후보 / 공개 가능`으로 분류하고, 아직 코드는 작성하지 말고 상용화 전환 설계부터 작성해줘.
