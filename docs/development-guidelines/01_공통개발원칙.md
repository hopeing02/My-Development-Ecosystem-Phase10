# **1.공통 개발 원칙 프롬프트 — 1차**

## **적용 대상**

이 개발 원칙은 다음 시스템에 공통 적용한다.

* 업무자동화허브  
* 프로젝트분석기  
* StudyHub

각 시스템의 목적과 데이터 구조는 다르지만 개발 방식, 데이터 저장, 관계 설계, 단계적 확장에는 동일한 원칙을 적용한다.

---

# **1\. 가장 중요한 개발 원칙**

전체 개발은 다음 두 가지 원칙을 최우선으로 한다.

**① 최소 구현으로 먼저 동작시킨다.**

**② 원본은 한 곳에만 저장하고 다른 곳에서는 ID로 연결한다.**

처음부터 완성형 구조를 만들려고 하지 않는다.

현재 버전에서 실제로 필요한 기능만 구현하고 정상 동작을 확인한 후 다음 버전에서 확장한다.

구조적 완벽함보다 다음 순서를 우선한다.

최소 구현 → 실행 → 실제 사용 → 검증 → 문제 발견 → 필요한 부분 개선 → 다음 기능 추가

---

# **2\. 초기 과설계를 하지 않는다**

개발 초기에 미래의 모든 기능을 예상하여 구조를 지나치게 복잡하게 만들지 않는다.

특히 다음과 같은 작업을 미리 하지 않는다.

* 아직 사용하지 않는 테이블 생성  
* 미래 기능을 위한 컬럼 대량 추가  
* 필요 여부가 확인되지 않은 공통화  
* 과도한 추상화  
* 불필요한 Interface 계층  
* 사용하지 않는 확장 포인트  
* 미래 API를 예상한 복잡한 구조  
* 필요하지 않은 설정 시스템  
* 모든 예외 상황을 처음부터 처리하려는 설계

현재 버전에 필요한 최소 구조만 만든다.

단, 향후 확장을 막는 명백한 구조적 문제는 피한다.

즉,

**확장 가능하게 만들되 확장 기능을 미리 만들지는 않는다.**

---

# **3\. 버전별 최소 구현을 기본으로 한다**

각 버전에는 명확한 목표를 하나 또는 소수만 둔다.

예:

v0.1 → 등록 가능

v0.2 → 조회 가능

v0.3 → 수정 가능

v0.4 → 관계 연결

v0.5 → 자동화

v0.6 → 통합 조회

와 같이 기능을 점진적으로 확장한다.

하나의 STEP에서 여러 기능을 한꺼번에 완성하려고 하지 않는다.

현재 버전의 기능이 정상 동작하면 일단 완료 상태로 만든다.

다음 기능은 다음 버전 또는 STEP에서 추가한다.

---

# **4\. 동작하는 최소 단위를 먼저 만든다**

새 기능을 구현할 때 가장 먼저 다음 질문을 한다.

"이 기능이 실제로 동작하기 위해 필요한 최소 구성은 무엇인가?"

그 최소 구성부터 구현한다.

예를 들어 등록 기능을 만든다면 처음부터 검색·수정·삭제·통계·대시보드까지 만들지 않는다.

등록 → 정상 저장 확인

까지만 먼저 완성한다.

그 후 필요에 따라

조회 → 수정 → 관계 → 자동화 → 통계 → UI 개선

순서로 확장한다.

---

# **5\. 미래 기능은 기록만 하고 구현하지 않는다**

개발 중 좋은 확장 아이디어가 나오더라도 현재 버전에 반드시 필요하지 않다면 바로 구현하지 않는다.

향후 기능으로 기록하고 현재 STEP을 먼저 완료한다.

예:

현재 필요한 기능 → 구현

곧 필요한 기능 → 다음 STEP 후보

나중에 필요할 가능성이 있는 기능 → 확장 아이디어로 기록

현재 필요성이 확인되지 않은 기능 → 구현하지 않음

이 원칙을 통해 기능이 계속 추가되어 현재 STEP이 끝나지 않는 문제를 방지한다.

---

# **6\. 각 데이터의 원본은 한 곳에만 둔다**

전체 시스템의 기본 데이터 원칙은 다음과 같다.

**원본은 한 곳에만 저장 → 다른 곳은 ID로 연결 → 필요한 시점에 조회·조합**

같은 정보를 여러 시트나 테이블에 반복 저장하지 않는다.

이미 존재하는 데이터를 다른 기능에서 사용해야 한다면 값을 복사하지 않고 ID를 통해 참조한다.

---

# **7\. 각 데이터의 소유자를 명확하게 한다**

각 데이터에는 하나의 원본 저장 위치가 있어야 한다.

업무자동화허브 예:

BusinessObject → ObjectId

WorkItem → WorkItemId

Person → PersonId

프로젝트분석기 예:

Project → ProjectId

File → FileId

AnalysisSession → SessionId

VersionHistory → VersionId

DevelopmentError → ErrorId

StudyHub 예:

Student → StudentId

Subject → SubjectId

StudyItem → StudyItemId

Concept → ConceptId

Problem → ProblemId

StudyLog → StudyLogId

다른 기능에서 필요한 경우 원본 데이터를 다시 저장하지 않고 ID로 연결한다.

---

# **8\. 이름보다 ID를 연결 기준으로 사용한다**

시스템 내부 관계는 이름이나 표시 문자열보다 ID를 기준으로 연결한다.

예:

WorkItem.ObjectId → BusinessObject.ObjectId

StudyItem.StudentId → Student.StudentId

VersionHistory.ProjectId → Project.ProjectId

이름은 표시값이고 ID는 관계값으로 취급한다.

다만 기존에 검증 완료된 이름 기반 구조가 있다면 즉시 전체를 변경하지 않는다.

신규 기능부터 ID 중심 원칙을 적용하고 기존 구조는 필요한 시점에 단계적으로 정리한다.

---

# **9\. 중복 컬럼을 만들지 않는다**

새 필드를 추가하기 전에 다음 순서로 확인한다.

1. 기존 시트 또는 테이블에 이미 존재하는가?  
2. ID로 조회할 수 있는가?  
3. 기존 데이터로 계산할 수 있는가?  
4. 실행 시 조합할 수 있는가?  
5. 해당 객체가 직접 소유해야 하는 데이터인가?

1\~4 중 하나로 해결할 수 있다면 원칙적으로 저장하지 않는다.

5에 해당하는 경우에만 새 필드를 추가한다.

---

# **10\. 조회 결과를 원본처럼 저장하지 않는다**

단순 조회나 화면 표시를 위해 새로운 결과 시트 또는 테이블을 만들지 않는다.

예:

업무 \+ 자료

프로젝트 \+ 파일

파일 \+ 버전

학생 \+ 과목 \+ 개념

학생 \+ 문제 \+ 오답

등의 통합 결과는 ID를 이용하여 실행 시 조합한다.

가능하면 Service 또는 UserForm에서 조회하여 표시한다.

---

# **11\. 관계 데이터는 관계만 저장한다**

관계 자체가 데이터라면 관계에 필요한 최소 정보만 저장한다.

예:

RelationId FromId RelationType ToId CreatedAt

다음과 같은 표시값은 중복 저장하지 않는다.

FromName ToName ObjectName ProjectName StudentName WorkItemTitle FileName SourcePath

필요할 때 원본에서 조회한다.

---

# **12\. 새 시트와 테이블 생성을 최소화한다**

새 기능이 생겼다는 이유만으로 새 시트나 테이블을 만들지 않는다.

다음 순서로 검토한다.

기존 기능 재사용 → 기존 데이터 활용 → ID 관계 활용 → 기존 Service 확장 → 실행 시 데이터 조합 → 그래도 독립적인 원본 데이터가 필요한 경우 새 저장소 생성

따라서 다음 공식을 사용하지 않는다.

새 기능 \= 새 시트

---

# **13\. 기존 검증 완료 코드를 보호한다**

사용자가 직접 실행하여 정상 동작을 확인한 코드는 검증 완료 코드로 취급한다.

검증 완료 코드는 다시 작성하지 않는다.

새 기능 구현 시 기존 함수를 우선 재사용한다.

기존 코드 변경이 반드시 필요하다면 먼저 다음을 확인한다.

* 변경 대상  
* 변경 이유  
* 기존 기능 영향  
* 재사용으로 해결 가능한지  
* 수정하지 않는 대안이 있는지

그 후 필요한 최소 범위만 수정한다.

---

# **14\. 시스템의 역할을 분리한다**

공통 개발 원칙을 사용하더라도 세 시스템의 역할은 유지한다.

업무자동화허브 → 업무·업무대상·사용자·관계·업무이력 관리

프로젝트분석기 → 프로젝트·파일·코드·버전·변경·분석·개발이력 관리

StudyHub → 학생·과목·개념·문제·오답·복습·학습이력·성취도 관리

한 시스템의 데이터를 다른 시스템에 그대로 복제하지 않는다.

---

# **15\. 시스템 간 연결도 느슨하게 유지한다**

향후 시스템을 연동하더라도 처음부터 하나의 거대한 시스템으로 합치지 않는다.

각 시스템은 독립적으로 동작할 수 있어야 한다.

필요할 때 ID, Mapping 또는 Adapter를 이용하여 연결한다.

구조는 다음 방향을 지향한다.

업무자동화허브 ↕ Adapter / Mapping ↕ 프로젝트분석기

StudyHub 역시 동일한 방식으로 독립성을 유지한다.

향후 API, SQLite, JSON, Python 등으로 확장할 수 있도록 시스템 간 결합도를 낮게 유지한다.

단, 현재 버전에서 시스템 간 연동이 필요하지 않다면 Adapter나 API를 미리 구현하지 않는다.

---

# **16\. 계층 구조도 필요한 만큼만 만든다**

기본적인 역할 분리는 유지한다.

예:

UI → Service → Repository → Data

하지만 작은 기능 하나를 위해 불필요한 계층과 클래스를 여러 개 만들지 않는다.

현재 기능 규모에서는 단순한 구조를 사용하고 기능이 실제로 복잡해질 때 분리한다.

즉,

**역할 분리는 하되 과도한 추상화는 하지 않는다.**

---

# **17\. VBA는 운영 가능한 최소 코드로 작성한다**

VBA 코드는 실제 업무에서 사용할 수 있는 운영 코드를 작성한다.

다음 원칙을 적용한다.

* 하드코딩된 테스트 데이터 최소화  
* 불필요한 MsgBox 제거  
* 불필요한 Debug 코드 제거  
* 기존 검증 함수 재사용  
* 필요한 수준의 오류 처리  
* 역할별 모듈 분리  
* 코드 중복 최소화

하지만 작은 기능을 구현하기 위해 지나치게 많은 공통 모듈을 새로 만들지 않는다.

---

# **18\. 기존 시스템을 한꺼번에 리팩터링하지 않는다**

새로운 원칙이 더 좋다는 이유만으로 기존 시스템 전체를 다시 작성하지 않는다.

다음 순서로 진행한다.

기존 정상 기능 보호 → 신규 기능에 새 원칙 적용 → 실제 사용 → 문제 확인 → 필요한 부분만 개선 → 안정화 후 선택적 리팩터링

리팩터링 자체가 개발 목적이 되지 않도록 한다.

---

# **19\. 실제 사용에서 필요성이 확인된 기능을 우선한다**

설계 단계에서 예상한 기능보다 실제 사용하면서 발견된 요구사항을 우선한다.

예상만으로 복잡한 기능을 미리 구현하지 않는다.

실제 사용 → 불편 발견 → 요구사항 확인 → 최소 개선

방식을 기본 개발 사이클로 사용한다.

---

# **20\. 한 STEP은 작게 유지한다**

하나의 STEP에는 가능하면 하나의 핵심 기능만 포함한다.

STEP 하나가 지나치게 커지면 여러 STEP으로 나눈다.

예:

STEP 1 등록

STEP 2 조회

STEP 3 수정

STEP 4 관계 연결

STEP 5 자동화

와 같이 나눈다.

각 STEP은 독립적으로 실행하여 정상 동작을 확인할 수 있어야 한다.

---

# **21\. 단계별 개발 답변 형식**

각 STEP의 답변은 다음 순서로 작성한다.

1. STEP 번호와 기능명  
2. 목적  
3. 기존 기능 중 재사용할 부분  
4. 추가 또는 수정할 모듈  
5. 최종 운영 코드  
6. 실행 방법  
7. 정상 동작 기준  
8. 다음 기능

설명은 필요한 내용만 간결하게 작성한다.

사용자가 정상 동작을 확인하면 해당 STEP을 검증 완료 상태로 간주한다.

이후 해당 코드는 재작성하지 않고 재사용한다.

---

# **22\. 새로운 기능 요청을 받았을 때 판단 순서**

새로운 기능 요청을 받으면 다음 순서로 판단한다.

현재 버전에 정말 필요한가? ↓ 더 작은 기능으로 나눌 수 있는가? ↓ 기존 기능을 재사용할 수 있는가? ↓ 기존 데이터로 해결할 수 있는가? ↓ ID 연결로 해결할 수 있는가? ↓ 새 컬럼이 정말 필요한가? ↓ 새 시트 또는 테이블이 정말 필요한가? ↓ 현재 단계에서 필요한 최소 구현은 무엇인가?

그리고 가장 작은 동작 가능한 형태부터 구현한다.

---

# **23\. 과설계 판단 기준**

다음과 같은 상황이 발생하면 과설계 가능성을 먼저 검토한다.

간단한 기능인데 새로운 모듈이 여러 개 필요함

하나의 기능 때문에 시트나 테이블이 여러 개 증가함

아직 사용하지 않는 필드가 많이 생김

미래 기능 때문에 현재 코드가 복잡해짐

사용자가 이해하기 어려울 정도로 계층이 증가함

실제 사용하지 않는 공통 Framework를 먼저 만들고 있음

현재 기능보다 기반 구조 개발량이 훨씬 커짐

이 경우 구조를 다시 단순화한다.

---

# **24\. 버전 완료 기준**

버전 완료의 기준은 "설계가 완벽한가"가 아니다.

다음 조건을 만족하면 현재 버전을 완료할 수 있다.

* 핵심 기능이 실제로 실행된다.  
* 데이터가 정상 저장 또는 조회된다.  
* 기존 검증 기능을 깨뜨리지 않는다.  
* 실제 업무 또는 학습에서 사용할 수 있다.  
* 다음 버전에서 확장할 수 있는 최소한의 구조가 있다.

현재 버전에서 필요하지 않은 기능이 남아 있다는 이유만으로 완료를 미루지 않는다.

**최소 설계 → 최소 구현 → 실행 → 검증 → 검증 완료 코드 고정 → 실제 사용 → 필요한 개선점 발견 → 다음 STEP → 다음 버전**

기능이 충분히 쌓인 후에만 전체 구조를 다시 검토한다.

그때 필요한 부분만 리팩터링한다.

# **26\. 1차 목표**

현재 목표는 업무자동화허브·프로젝트분석기·StudyHub의 최종 완성형을 처음부터 설계하는 것이 아니다.

각 시스템이 실제로 동작하는 버전을 빠르게 만들고 사용하면서 점진적으로 발전시키는 것이 목표다.

최종적으로 다음 원칙을 유지한다.

**작게 설계한다.**

**작게 구현한다.**

**먼저 동작시킨다.**

**검증된 코드는 재사용한다.**

**필요해졌을 때 확장한다.**

**데이터 원본은 한 곳에 둔다.**

**다른 데이터는 ID로 연결한다.**

**조회 시 조합한다.**

**시스템은 독립성을 유지한다.**

**과설계보다 실제 동작과 점진적 개선을 우선한다.**

이 원칙을 업무자동화허브, 프로젝트분석기, StudyHub의 모든 신규 버전과 STEP에 공통 적용한다.

# **2차 공통 개발 규격**

업무자동화허브, 프로젝트분석기, StudyHub의 신규 기능은 다음 공통 규격을 따른다.

이 규격은 기존 검증 완료 코드를 변경하기 위한 것이 아니다.

**기존 검증 완료 코드는 그대로 유지하고 신규 기능부터 적용한다.**

---

## **1\. ID 규칙**

각 시스템의 기존 ID 체계는 그대로 유지한다.

기존 ID를 공통 규격에 맞추기 위해 변경하거나 재발급하지 않는다.

신규 ID는 다음 원칙을 따른다.

* ID는 생성 후 변경하지 않는다.  
* 표시명 변경과 ID 변경을 분리한다.  
* 삭제된 ID를 재사용하지 않는다.  
* 동일 EntityType 내에서 ID가 중복되지 않도록 한다.  
* 행 번호, 셀 주소, 파일 경로, 이름을 ID로 사용하지 않는다.  
* 신규 EntityType의 ID는 가능하면 `PREFIX-NUMBER` 형식을 사용한다.  
* Prefix는 EntityType별로 일관되게 사용한다.  
* 필요하지 않은 EntityType과 Prefix를 미리 만들지 않는다.

시스템 간 객체 참조는 내부 ID 하나만 사용하지 않고 다음 EntityRef를 사용한다.

EntityRef  
\- SystemId  
\- EntityType  
\- EntityId

예:

WORKHUB / BUSINESS\_OBJECT / BO-000015  
PROJECT\_ANALYZER / FILE / FILE-000125  
STUDYHUB / STUDY\_ITEM / SI-000023

서로 다른 시스템에서 같은 EntityId가 존재해도 허용한다.

전체 객체의 식별은 `SystemId + EntityType + EntityId` 조합으로 판단한다.

---

## **2\. Repository / Service 규칙**

신규 기능은 가능한 범위에서 다음 책임 구조를 따른다.

UI / Entry Point  
        ↓  
     Service  
        ↓  
   Repository  
        ↓  
Excel / SQLite / File

### **UI / Entry Point**

UI는 다음 역할만 담당하도록 한다.

* 사용자 입력  
* Service 호출  
* 실행 결과 표시

신규 UI 코드에 업무 규칙이나 복잡한 저장소 접근을 직접 넣지 않는다.

### **Service**

Service는 업무 동작과 규칙을 담당한다.

예:

AddWorkItem  
ChangeWorkItemStatus

StartAnalysis  
SaveDevelopmentError

AddStudyItem  
CompleteStudyItem

Service의 주요 책임:

* 입력 검증  
* 업무 규칙  
* 상태 변경  
* 필요한 Repository 호출  
* 여러 작업의 조합  
* 실행 결과 반환

### **Repository**

Repository는 데이터의 저장과 조회를 담당한다.

예:

FindById  
ExistsById  
Insert  
Update  
Delete

필요한 함수만 만든다.

CRUD 전체를 미리 구현하지 않는다.

Excel Repository는 시트, 행, 셀 접근을 담당할 수 있다.

SQLite Repository는 SQL 실행과 데이터 조회·저장을 담당할 수 있다.

업무 판단 로직은 Repository에 넣지 않는다.

---

## **3\. 과도한 공통 계층 생성 금지**

현재 단계에서는 다음 구조를 미리 만들지 않는다.

BaseRepository  
GenericRepository  
RepositoryFactory  
BaseService  
ServiceFactory  
공통 Framework

실제 중복과 재사용 필요성이 확인된 경우에만 Common Core 후보로 검토한다.

**역할은 통일하지만 구현까지 미리 통합하지 않는다.**

---

## **4\. 기존 검증 코드 예외**

기존 검증 완료 코드가 새로운 Repository / Service 구조와 다르더라도 구조 통일만을 목적으로 수정하지 않는다.

예:

기존

UI  
 ↓  
기존 Module  
 ↓  
Excel

가 정상 동작한다면 그대로 유지할 수 있다.

신규 기능에서는:

UI  
 ↓  
Service  
 ↓  
Repository  
 ↓  
Storage

구조를 가능한 범위에서 적용한다.

기존 기능이 필요한 경우 신규 Service가 기존 검증 함수를 호출하는 방식도 허용한다.

## **6\. JSON 외부 교환 규칙**

JSON은 현재 내부 저장 방식이 아니라 **향후 MDE 및 시스템 간 데이터 교환 규격**으로 사용한다.

내부 VBA나 SQLite 구조를 JSON 구조에 맞추기 위해 변경하지 않는다.

JSON 필드명은 `camelCase`를 사용한다.

EntityRef 기본 형식:

{  
  "systemId": "WORKHUB",  
  "entityType": "BUSINESS\_OBJECT",  
  "entityId": "BO-000015"  
}

Relation 기본 형식:

{  
  "relationId": "REL-000001",  
  "fromRef": {  
    "systemId": "WORKHUB",  
    "entityType": "BUSINESS\_OBJECT",  
    "entityId": "BO-000015"  
  },  
  "relationType": "ANALYZED\_BY",  
  "toRef": {  
    "systemId": "PROJECT\_ANALYZER",  
    "entityType": "PROJECT",  
    "entityId": "PRJ-000003"  
  },  
  "createdAt": "2026-09-23T17:50:00+09:00"  
}

날짜·시간의 외부 교환 형식은 ISO 8601을 기본으로 한다.

내부 Excel Date 또는 기존 저장 형식은 변경하지 않는다.

필요할 때 Adapter가 변환한다.

---

## **7\. MDE Adapter 규칙**

MDE는 각 시스템의 내부 저장 구조에 직접 접근하지 않는다.

금지:

MDE  
→ Excel 특정 시트/열 직접 접근

MDE  
→ SQLite 내부 테이블 구조 직접 의존

기본 구조:

MDE  
 ↓  
Common Contract / JSON  
 ↓  
MDE Adapter  
 ↓  
Service  
 ↓  
Repository  
 ↓  
Storage

Adapter는 다음 역할만 담당한다.

* 내부 데이터 → Common Contract 변환  
* Common Contract → 내부 호출 형식 변환  
* EntityRef 변환  
* JSON 외부 표현 변환

업무 규칙은 Adapter에 넣지 않는다.

---

## **8\. Common Core 분리 규칙**

공통 기능처럼 보인다는 이유만으로 바로 Common Core로 이동하지 않는다.

다음 기준을 사용한다.

한 시스템에서 사용  
→ Domain 유지

두 시스템에서 비슷한 기능 발견  
→ 공통화 후보로 관찰

여러 시스템에서 동일 의미와 동작 반복  
→ Common Core 분리 검토

코드 모양만 비슷한 것이 아니라 **업무 의미까지 동일한 경우**에 공통화를 검토한다.

Common Core 후보 예:

* ID 생성/검증  
* EntityRef  
* Relation 공통 처리  
* Version 공통 처리  
* Diff  
* Result  
* Audit  
* Export

실제 필요성이 확인되기 전에는 구현하지 않는다.

\#\# 13\. 향후 확장 예약 원칙

다음 기능은 향후 공통 확장 후보로만 기록한다.  
현재 단계에서는 Contract, 테이블, 시트, 모듈 또는 공통 코드를 구현하지 않는다.

\- ActionLog  
  사용자 또는 시스템이 수행한 의미 있는 행동 기록

\- Experience  
  행동 및 처리 결과를 경험 데이터로 축적

\- Feedback  
  처리 결과에 대한 성공, 실패, 평가 또는 피드백 기록

\- Score  
  누적 이력을 이용한 규칙 기반 점수 계산

\- Recommendation  
  누적 이력과 규칙을 이용한 추천 결과

이 기능들의 장기적인 확장 방향은 다음과 같다.

ActionLog  
    ↓  
Experience / Feedback  
    ↓  
통계  
    ↓  
Rule / Score  
    ↓  
Pattern  
    ↓  
Recommendation  
    ↓  
향후 Local LLM / RAG / 외부 AI

초기 단계에서는 AI를 사용하지 않는다.

반복 횟수, 성공률, 오답률, 최근 사용 이력,  
처리 시간, 상태 변화 등의 실제 데이터를 이용하여  
규칙 및 통계 기반으로 동작할 수 있도록 한다.

각 시스템의 활용 예:

업무자동화허브  
\- 반복 업무 행동 기록  
\- 자동화 후보 발견  
\- 자주 사용하는 업무 절차 파악  
\- 향후 Recipe / Code Builder 연결

프로젝트분석기  
\- 코드 변경 및 분석 행동 기록  
\- 오류 → 수정 → 검증 이력 축적  
\- 변경 패턴 및 영향 관계 분석

StudyHub  
\- 문제 풀이 및 복습 행동 기록  
\- 오답 반복 패턴  
\- 개념별 취약도  
\- 복습 우선순위 계산

단, 위 기능 때문에 현재 시스템 개발을 중단하거나  
기존 검증 완료 코드를 수정하지 않는다.

공통화 기준 역시 기존 원칙을 따른다.

한 시스템에서 먼저 필요  
→ 해당 Domain에서 최소 구현

두 시스템 이상에서 동일 의미 반복  
→ 공통화 후보로 관찰

여러 시스템에서 실제 재사용 필요 확인  
→ Common Contract / Common Core 분리 검토

따라서 현재 공통 설계 종료선은 그대로 유지한다.  
ActionLog, Experience, Feedback, Score, Recommendation은  
향후 확장 후보이며 현재 구현 대상이 아니다.

\#\# 14\. VBA → Python 향후 이관 원칙

현재 내부망 VBA 시스템은 향후 외부망 Python 환경으로  
기능 단위 이관할 수 있도록 개발한다.

단, Python 이관을 위해 현재 VBA 구조를 복잡하게 만들거나  
기존 검증 완료 코드를 수정하지 않는다.

기본 원칙은 다음과 같다.

1\. VBA 코드를 Python 문법으로 1:1 변환하는 것을 목표로 하지 않는다.

2\. 이관 단위는 코드가 아니라 기능과 Contract로 한다.

3\. 업무 규칙은 가능한 범위에서 UI 및 저장소 접근과 분리한다.

4\. Excel Cells, Range, Worksheet 등 VBA/Excel 종속 코드는  
   가능한 범위에서 Repository 또는 UI 영역에 둔다.

5\. Service의 입력, 처리 규칙, 결과 의미는  
   Python에서도 동일하게 재현할 수 있도록 한다.

6\. 시스템 간 교환이 필요한 경우 Common Contract를 기준으로 한다.

7\. 외부 교환이 필요한 시점에는 JSON / Adapter를 사용한다.

8\. Python 이관을 예상하여 현재 사용하지 않는  
   Interface, Adapter, API, Framework를 미리 구현하지 않는다.

9\. 기존 검증 완료 VBA 코드는 Python 이관을 이유로  
   재작성하거나 리팩터링하지 않는다.

10\. Python판은 VBA판의 소스코드 복사본이 아니라  
    동일한 기능 규격을 구현하는 별도 구현체로 본다.

11\. 전체 시스템을 한 번에 이관하지 않는다.

    기능 선택  
       ↓  
    현재 VBA 동작 확인  
       ↓  
    입력 / 규칙 / 결과 정의  
       ↓  
    Python 최소 구현  
       ↓  
    동일 결과 검증  
       ↓  
    다음 기능 이관

12\. VBA판과 Python판은 필요하면 일정 기간 병행 운영할 수 있다.

13\. HTML / CSS / JS 등 환경에 독립적인 UI 자산은  
    재사용 가능성을 우선 검토한다.

14\. Python에서 더 적합한 구현 방식이 있다면  
    VBA 구조를 그대로 복제하지 않고 Python 환경에 맞게 구현한다.

목표 구조:

                 Common Contract  
                        │  
                기능 / 업무 규칙  
                        │  
          ┌─────────────┴─────────────┐  
          │                           │  
     내부망 VBA                  외부망 Python  
          │                           │  
   Excel / SQLite              SQLite / DB / File

현재 목표는 Python판을 미리 구현하는 것이 아니다.

현재 VBA 시스템을 실제 사용 가능한 수준으로 계속 개발하면서  
향후 기능 단위 이관을 방해하는 불필요한 결합만 피한다.

자료구조·검색·그래프·통계·추천 등의 알고리즘은 실제 기능의 정확성·성능·자동화 수준을 실질적으로 개선하는 경우 우선 검토하되, 기술 자체를 목적으로 선행 구현하지 않는다.

기존 검증 완료 함수의 재사용을 최우선으로 하고, 신규 함수는 해당 STEP 구현에 반드시 필요한 경우에만 생성한다

# **검증 완료 코드 실제 재사용 및 Common Core 승격 규칙**

신규 기능을 구현할 때 기존 시스템의 구조만 참고하여 유사 코드를 새로 작성하는 것을 우선하지 않는다.

먼저 업무자동화허브, 프로젝트분석기, StudyHub의 기존 검증 완료 코드에 동일하거나 거의 동일한 기능이 존재하는지 확인한다.

기존 검증 완료 함수가 존재하면 반드시 해당 함수의 실제 원문과 역할을 확인한 후 다음과 같이 판단한다.

## **1\. Domain 코드**

WorkItem, BusinessObject, StudyItem, Parser, CallTree 등 특정 시스템의 업무 의미에 종속된 코드는 해당 시스템의 Domain 코드로 유지한다.

다른 시스템에서 구조가 비슷하다는 이유만으로 복사하거나 Common Core로 이동하지 않는다.

## **2\. 범용 코드**

특정 업무 의미에 종속되지 않고 여러 시스템에서 동일하게 사용할 수 있는 검증 완료 함수는 Common Core 후보로 등록한다.

예:

* ID 생성 및 검증  
* ID 기준 행 또는 객체 검색  
* 중복 검사  
* 공통 문자열 처리  
* 공통 날짜 처리  
* Relation 공통 처리  
* Version/Diff 공통 처리  
* Result 처리  
* 범용 파일 처리

## **3\. 실제 코드 재사용 원칙**

"구조를 참고하여 새로 작성한 코드"와 "기존 검증 완료 코드의 실제 재사용"을 명확히 구분한다.

기존 함수의 원문을 확인하지 않은 경우 검증 완료 코드를 재사용했다고 판단하지 않는다.

가능하면 동일 기능을 새로 작성하기 전에 기존 검증 완료 함수 원문을 그대로 재사용한다.

## **4\. Common Core 승격**

검증 완료 범용 함수를 Common Core로 이동할 필요가 생기더라도 기존 운영 코드를 즉시 삭제하거나 변경하지 않는다.

다음 순서로 진행한다.

기존 검증 완료 함수 확인 → 범용성 확인 → Common Core 후보 등록 → 검증된 원문을 Common Core 기준본으로 지정 → 다른 시스템에서 동일 Core 사용 → 정상 동작 검증 → 기존 시스템 호출부를 단계적으로 Core 호출로 전환 → 모든 영향 확인 후에만 기존 중복 코드 제거

## **5\. Common Core 원본 관리**

Common Core 함수는 시스템별로 따로 수정하지 않는다.

하나의 기준 원본을 유지한다.

예:

CommonCore/

* modCoreId.bas  
* modCoreLookup.bas  
* modCoreText.bas  
* modCoreRelation.bas  
* modCoreVersion.bas

업무자동화허브, 프로젝트분석기, StudyHub에서는 필요한 Common Core 모듈의 동일 원문을 사용한다.

각 시스템에서 Core 코드를 독자적으로 수정하여 서로 다른 버전으로 분기시키지 않는다.

## **6\. 신규 STEP 구현 전 확인**

신규 코드를 작성하기 전에 다음 순서로 확인한다.

기존 검증 완료 함수 존재 여부 → 실제 원문 확인 → 그대로 재사용 가능한가? → Domain 종속 코드인가? → 범용 코드인가? → Common Core 후보인가? → 필요한 최소 신규 코드만 작성

기존 검증 완료 함수로 해결할 수 있다면 같은 기능의 신규 함수를 만들지 않는다.

## **7\. 과도한 Core화 금지**

Common Core를 만들기 위해 기존 시스템 전체를 리팩터링하지 않는다.

실제 재사용이 필요한 검증 완료 함수부터 하나씩 승격한다.

Common Core 분리 자체가 현재 기능 개발을 지연시키지 않도록 한다.

**구조 재사용보다 검증 코드 재사용을 우선하되, Domain 코드는 분리하고 실제 범용성이 확인된 함수만 Common Core로 승격한다.**

# **15\. 보안 및 내부망 데이터 처리 원칙**

업무자동화허브, 프로젝트분석기, StudyHub 및 향후 추가되는 내부 업무도구는 회사의 정보보안 정책과 사용자의 기존 접근권한을 우선한다.

기능 구현을 위해 회사의 보안통제, 접근권한 또는 인증절차를 우회하지 않는다.

## **1\. 기본 원칙**

다음 순서를 우선한다.

정상 접근권한 → Read-Only 조회 → 최소 정보 수집 → 내부 처리 → ID/링크 중심 연결 → 변경이력 기록

자동화 편의성을 이유로 보안 수준을 낮추지 않는다.

## **2\. 접근권한**

사용자가 정상적인 업무 절차를 통해 접근할 수 있는 자료만 처리한다.

다음을 구현하지 않는다.

* 접근권한 우회  
* 인증절차 우회  
* 다른 사용자의 권한 사용  
* 세션 탈취 또는 임의 재사용  
* 보안통제 회피  
* 접근이 제한된 자료의 강제 수집

사이트 자동접속이 회사 정책상 허용되지 않는 경우 자동화를 구현하지 않는다.

이 경우 원본 사이트 열기 → 사용자 확인 → 확인일 기록 방식으로 처리한다.

## **3\. 인증정보**

ID, 비밀번호, OTP, 인증서 비밀번호 등의 인증정보를 VBA 코드, Excel 시트, 설정파일 등에 평문으로 저장하지 않는다.

가능하면 회사가 제공하는 기존 로그인 상태와 정상적인 인증절차를 그대로 사용한다.

인증정보 저장이 필요한 기능은 회사 보안정책에서 허용되는 공식적인 방법이 확인되기 전에는 구현하지 않는다.

## **4\. 원본 데이터**

회사 시스템의 원본은 기존 시스템에 그대로 유지한다.

업무자동화허브는 원본 시스템을 대체하는 저장소로 사용하지 않는다.

가능하면 다음 정보만 관리한다.

* SourceId  
* SourceType  
* SourceURL 또는 내부 경로  
* Title  
* EntityRef  
* Tag  
* LastCheckedAt  
* LastModifiedAt  
* ContentHash  
* Status

원문 전체 저장이 반드시 필요한 경우에만 별도로 저장한다.

## **5\. 원본 수정 금지**

외부 시스템 및 회사 사이트에 대한 기본 동작은 Read-Only로 한다.

변경감지, 검색, 색인, 관계 연결 등의 기능이 원본 자료를 수정하거나 삭제하지 않도록 한다.

원본 시스템의 수정 기능이 실제 업무상 필요한 경우 별도의 기능으로 분리하고 명시적인 사용자 실행을 요구한다.

## **6\. 최소 수집**

업무 목적에 필요한 최소 데이터만 수집한다.

단순 변경감지를 위해 원문 전체를 영구 저장할 필요가 없다면 다음과 같은 메타데이터만 저장한다.

문서ID 제목 수정일 Hash 마지막 확인일

새로운 데이터 항목을 저장하기 전에 기존 공통 개발 원칙의 중복 저장 및 원본 단일화 규칙을 적용한다.

## **7\. 개인정보 및 중요정보**

주민등록번호, 계좌번호, 연락처 및 회사에서 중요정보로 분류하는 자료는 검색 편의를 위해 불필요하게 복제하거나 색인하지 않는다.

업무상 반드시 필요한 경우에도 회사 보안정책에서 허용되는 범위만 처리한다.

검색 인덱스, 로그, 임시파일 등에 중요정보가 의도하지 않게 남지 않도록 한다.

## **8\. 외부 전송 금지**

회사 내부 자료를 승인되지 않은 외부 서비스로 자동 전송하지 않는다.

특히 다음 작업은 별도의 승인이나 명확한 회사 정책 확인 없이 구현하지 않는다.

* 외부 AI 서비스로 회사 원문 전송  
* 개인 클라우드 업로드  
* 개인 이메일 전송  
* 외부 서버 백업  
* 외부 API로 내부자료 전송

내부망 VBA 버전은 기본적으로 내부망 안에서 독립적으로 동작하도록 한다.

## **9\. 변경감지**

회사 사이트의 변경감지는 가능한 경우 다음 순서로 구현한다.

공식 수정일/버전 확인 → 게시물 또는 문서 ID 비교 → 파일 메타데이터 비교 → 필요한 경우 Hash 비교 → 필요한 경우에만 내용 비교

단순 변경감지를 위해 매번 원문 전체를 별도 DB에 복제하지 않는다.

변경감지는 원본 수정 없이 Read-Only 방식으로 수행한다.

## **10\. 자동수집 제한**

사이트 전체를 무차별적으로 수집하지 않는다.

실제 업무에서 필요한 페이지, 게시판 또는 문서부터 감시 대상으로 등록한다.

예:

감시대상 등록 → 정상 접근 → 최소 정보 조회 → 이전 상태 비교 → 변경 여부 저장 → 사용자에게 표시

사이트 부하를 증가시키는 과도한 반복 요청을 하지 않는다.

## **11\. 감사 및 추적**

자동으로 수집하거나 갱신하는 기능에는 필요한 범위에서 다음 정보를 기록할 수 있다.

* 실행시각  
* SourceId  
* 처리유형  
* 이전 상태  
* 현재 상태  
* 처리결과

단순 Debug 로그를 무분별하게 축적하지 않는다.

로그에도 개인정보나 인증정보를 저장하지 않는다.

## **12\. 자동화 가능 여부 판단**

새로운 회사 사이트 또는 내부 시스템을 연결할 때 다음 순서로 판단한다.

업무상 필요한가? ↓ 사용자에게 정상 접근권한이 있는가? ↓ 회사 정책상 자동접근이 허용되는가? ↓ Read-Only로 구현 가능한가? ↓ 원문 복사 없이 ID/링크/메타데이터만으로 가능한가? ↓ 개인정보 또는 중요정보가 포함되는가? ↓ 외부 전송 없이 처리 가능한가? ↓ 필요한 최소 기능만 구현

하나라도 보안상 불명확하면 자동화를 확대하지 않고 수동 확인 방식 또는 기존 시스템 링크 방식으로 유지한다.

## **13\. 기존 시스템과의 관계**

기존 회사 시스템은 원본 Source로 유지한다.

업무자동화허브는 그 위에 다음 기능을 제공하는 개인 업무 지식 계층으로 구성한다.

기존 회사 시스템 ↓ Read-Only Source ↓ 업무자동화허브 ↓ 색인 / 검색 / 관계 / 태그 / 변경감지 / 업무매뉴얼

기존 시스템의 보안정책과 권한체계를 변경하지 않는다.

## **14\. 보안과 기능이 충돌할 경우**

편의성과 보안이 충돌하면 보안을 우선한다.

자동화가 불가능하더라도 다음과 같은 안전한 대체 방법을 우선 검토한다.

자동수집 → 변경여부만 확인

전체 원문 저장 → 링크 및 메타데이터 저장

자동 로그인 → 기존 로그인 세션에서 사용자 실행

자동 변경 → 변경 후보 표시 후 사용자 확인

완전자동화 → 반자동화

목표는 회사 시스템을 우회하는 것이 아니라 기존 권한과 보안정책 안에서 사용자의 정보 탐색과 업무처리를 효율화하는 것이다.

앞으로 내부망 개발에서는 코드 전문이나 원문을 달라고 요청하지 않겠습니다.  
필요한 경우에도 함수명, 매개변수/반환값, 시트·컬럼명, 오류 메시지, 실행 결과처럼 반출 가능한 최소 정보만으로 진행하겠습니다. 실제 기존 코드와의 대조가 필요하면 제가 내부망에서 직접 확인할 체크포인트를 드리고, 확인 결과만 알려주시면 됩니다.
