## 실제 문제

개발 중 남긴 짧은 기록에 설명을 더하고 싶다고 해서 기본판을 다시 쓰면, 어느 내용이 처음 기록이고 어느 내용이 나중 해설인지 구분하기 어려워진다. 기본판의 파일을 보호하고 해설을 별도 입력으로 받으면 두 목적을 함께 지킬 수 있다.

또 하나의 문제는 예시 이름을 실제 계약으로 착각하는 것이다. 기존 manifest는 책의 `title`과 `chapters` 안의 `title`, `path`를 받는다. 별도 STEP ID 필드가 없으므로 보충 목록의 `step`에 `STEP-01`을 적어도 연결되지 않는다. 실제 장 앵커인 `chapter-001`을 써야 첫 장을 찾는다.

이때 승인은 AI가 판단하는 값이 아니다. 사용자가 검토한 보충 파일을 별도 JSON 목록에 명시하는 것으로 표현한다. 프로그램은 그 목록과 파일을 검증해 조립한다. 해설을 검색하거나 AI가 해설을 새로 쓰지 않는다.

## 변경 전

부모 버전의 `build_ebook`은 `manifest_path`, `output_dir`, 키워드 전용 `overwrite: bool = False`를 받았다. 원고를 목록 순서로 읽고 `toc.md`와 `basic.md`를 생성했다. `supplements_path` 인자와 `--supplements` CLI는 없었다.

`_read_manifest`는 JSON과 원고를 읽고 누락·빈 원고·중복 파일 등을 검사한다. `_title`은 비어 있지 않은 한 줄 제목을 확인하며, `_markdown_text`는 제목과 목차 표시문자를 이스케이프한다. 반환형 `BuildResult`에는 `toc_path`, `basic_path`, `chapter_count` 세 필드가 있다. 이 함수들과 반환형은 새 기능에서도 그대로 재사용한다.

기본판은 각 장에 `chapter-001`, `chapter-002` 순서의 앵커를 넣는다. 별도 `toc.md`의 링크는 `basic.md`를 가리킨다. 본문은 UTF-8 BOM 제거와 개행 LF 통일 외에는 보존한다. 이 기반을 고쳐 새 전자책 엔진을 만들 필요는 없었다.

## 변경 후

추가된 `_read_supplements`는 승인 목록의 형식과 장 연결, 경로 경계를 검증한다. `build_ebook`은 선택 입력을 받고 기존 장별 텍스트 조각을 기본판과 확장판에 함께 사용한다. `main(argv: list[str] | None = None) -> int`는 기존 CLI에 `--supplements`를 더해 그 값을 `supplements_path`로 전달한다. 새 클래스나 별도 파서·프레임워크를 만들지 않았다.

보충 JSON은 `supplements` 배열에 `step`과 `path`를 담는다. 공개 예제는 `step`이 `chapter-001`이고 `path`가 `supplements/STEP_01_explanation.md`다. **이 path의 기준은 보충 JSON 위치가 아니라 원고 manifest가 있는 폴더다.** 현재 작업 폴더도 기준이 아니다. 보충 JSON을 다른 폴더로 옮겨도 원고 manifest가 같으면 같은 보충 파일을 가리킨다.

확장판은 원래 장 본문을 넣고, 승인 해설이 있는 장 뒤에만 `### 추가 해설`과 보충 본문을 붙인다. 첫 장만 목록에 있으면 둘째 장에는 이 제목이 생기지 않는다. 표·코드·한글도 기존 본문 처리 규칙에 따라 보존한다. 기본판과 확장판에는 같은 내부 목차와 장 앵커가 있고, 별도 `toc.md`는 계속 기본판을 가리킨다.

| 호출 조건 | 실제 동작 |
| --- | --- |
| `supplements_path` 없음 | STEP 01의 생성·덮어쓰기·반환 동작 유지. 기존 `expanded.md`도 생성·수정·삭제하지 않음 |
| 확장 모드, 기존 toc/basic이 예상 바이트와 같음 | 읽어서 확인한 뒤 다시 쓰지 않음 |
| 확장 모드, 기존 toc/basic이 예상 바이트와 다름 | `overwrite=True` 또는 `--overwrite`여도 실패하고 보존 |
| 확장 모드, toc/basic 중 없는 파일 | 기존 렌더링으로 없는 파일을 배타 생성 |
| 확장 모드, 기존 expanded가 있음 | 기본값은 실패. `overwrite=True`일 때 `expanded.md`만 교체 |

반환형도 `BuildResult` 그대로다. 확장판 경로를 담는 새 필드는 없으며 호출자가 `output_dir / "expanded.md"`로 찾는다.

STEP 03의 결과는 이미 생성된 `MDE-PHASE10-001.md` 한 파일이다. 이 원고는 기존 입력 검사 함수를 재사용한 공개 API 호환 변경을 설명하고, 운영 코드 발췌·가상 실습·과거 검사 기록·검증 대기 상태를 나눈다. 이 커밋에서 문서 파일이 추가되었다는 사실과, 그 원고가 설명하는 과거 기능이 오늘 새로 구현되었다는 주장은 서로 다르다. STEP 03이 자동 AI 집필 기능을 제작기에 추가한 것도 아니다.

집필 작업을 제한하는 W1 계약은 기존 `run_codex_single_task.py`와 `CODE-015`에서 확인할 수 있다. 실행기는 clean worktree에서 HEAD를 기준으로 삼고, `allowedFiles`를 프롬프트에 넣는다. Codex 종료 후와 각 외부 검증 명령 후에 변경 경로와 HEAD를 다시 검사한다. 검증 명령은 argv 배열로 실행하며, 실패하면 다음 명령을 실행하지 않고 변경을 검토 증거로 남긴다.

W1의 결과 계약에는 `success`, 작업·STEP ID, `changedFiles`, `disallowedFiles`, 명령별 `validationResults` 등이 있다. 그러나 이 계약의 존재만으로 STEP 03의 실제 W1 `result.json`이 저장소에 커밋되어 있다고 말할 수 없다. 지정 커밋의 자료로는 그 실행 결과를 확인했다고 주장하지 않는다. W1 코드·문서는 기존 운영 방식의 참고 근거이며 오늘 새로 구현한 파일이 아니다.

## 따라 하기

저장소 루트에서 Python 3.12 이상이 준비된 PowerShell로 실행하는 **독자용 가상 실습**이다. 운영 코드 원문이 아니며, 문서 작성 단계에서는 실행하지 않는다. 편집자는 집필이 끝난 뒤 별도로 실행할 수 있다. 실제 파일이나 판매 원고를 입력으로 읽지 않고, 실습에서 만든 가상 MD 세 개와 JSON 두 개만 사용한다.

두 장의 기본판을 먼저 만든 다음 같은 출력 폴더에 확장판을 추가한다. 보충 JSON을 일부러 `approval` 폴더에 두어도 보충 `path`가 manifest 폴더 기준임을 확인할 수 있다. 예제에는 새 함수나 클래스를 정의하지 않는다.

```powershell
@'
import json
from pathlib import Path
from tempfile import TemporaryDirectory

from apps.ebook_ai.ebook_builder import build_ebook

with TemporaryDirectory() as temporary_directory:
    root = Path(temporary_directory)
    (root / "notes").mkdir()
    (root / "approval").mkdir()
    (root / "first.md").write_text("FIRST_BODY\n", encoding="utf-8")
    (root / "second.md").write_text("SECOND_BODY\n", encoding="utf-8")
    (root / "notes" / "first.md").write_text(
        "APPROVED_FIRST_NOTE\n", encoding="utf-8"
    )
    manifest = root / "manifest.json"
    manifest.write_text(
        json.dumps({
            "title": "Daily practice",
            "chapters": [
                {"title": "First", "path": "first.md"},
                {"title": "Second", "path": "second.md"},
            ],
        }),
        encoding="utf-8",
    )
    approved = root / "approval" / "supplements.json"
    approved.write_text(
        json.dumps({
            "supplements": [
                {"step": "chapter-001", "path": "notes/first.md"},
            ],
        }),
        encoding="utf-8",
    )
    output = root / "output"
    basic_result = build_ebook(manifest, output)
    toc_before = basic_result.toc_path.read_bytes()
    basic_before = basic_result.basic_path.read_bytes()
    assert not (output / "expanded.md").exists()

    expanded_result = build_ebook(manifest, output, supplements_path=approved)
    assert expanded_result == basic_result
    assert basic_result.toc_path.read_bytes() == toc_before
    assert basic_result.basic_path.read_bytes() == basic_before
    assert basic_result.chapter_count == 2
    expanded = (output / "expanded.md").read_text(encoding="utf-8")
    extra_heading = "### " + "\uCD94\uAC00 \uD574\uC124"
    first_anchor = '<a id="chapter-001"></a>'
    second_anchor = '<a id="chapter-002"></a>'
    first_part = expanded.split(first_anchor, 1)[1].split(second_anchor, 1)[0]
    second_part = expanded.split(second_anchor, 1)[1]
    basic_second_part = basic_before.decode("utf-8").split(second_anchor, 1)[1]
    assert expanded.count(extra_heading) == 1
    assert first_part.index("FIRST_BODY") < first_part.index(extra_heading)
    assert first_part.index(extra_heading) < first_part.index("APPROVED_FIRST_NOTE")
    assert extra_heading not in second_part
    assert "APPROVED_FIRST_NOTE" not in second_part
    assert "SECOND_BODY" in second_part
    assert second_part == basic_second_part
    print('DAILY_EXERCISE_PASS')
'@ | python -B -
```

문자열 `\uCD94\uAC00 \uD574\uC124`은 Python에서 `추가 해설`이 된다. 실습 입력과 명령 안의 문자열을 ASCII로 적어 PowerShell의 파이프 문자 인코딩 영향을 줄였다. `python -B`는 import 과정에서 바이트코드를 만들지 않는다. 파일 내용은 `encoding="utf-8"`로 읽고 쓴다.

모든 assert가 통과하면 마지막에 `DAILY_EXERCISE_PASS`가 출력된다. 이는 위 가상 시나리오가 통과했을 때의 예상 결과다. 이번 집필에서 얻은 실행 결과는 아니다. `TemporaryDirectory`는 블록을 벗어날 때 실습 파일을 정리한다.

## 검증

직접 읽은 `test_expanded_edition.py`는 단순히 파일이 생기는지만 검사하지 않는다. 첫 장 뒤의 해설 위치와 둘째 장 유지, 기본판·목차의 바이트·mtime·inode 보존, 모든 입력 파일 보존을 확인한다. STEP 01 예제 출력의 SHA-256도 고정해 이전 출력과의 호환성을 검사한다. 재생성·덮어쓰기, 잘못된 승인 목록, 경로 이탈, 입출력 별칭, 교체 실패, 경쟁 게시, CLI 실패 처리도 다룬다.

다음 수치는 **지정 커밋의 EBOOK-AI-02 문서가 기록한 과거 검사**다. 이번 집필에서 pytest·Ruff·Black을 다시 실행해 얻은 결과가 아니다.

| Git 공백 검사 | `git diff --check` 통과 |

해당 기록에서는 루트 기본 testpaths에 전자책 앱이 포함되지 않아 앱 검사를 별도로 실행했다고 설명한다. 루트의 skip을 확장판 검사 skip으로 옮겨 적지 않는다. 이번 출판 전 별도 검사도 사용자 전달상 `73 passed`였지만, 위 표는 그 별도 실행이 아닌 커밋된 검증 문서를 근거로 한다. 집필 자체가 앱 전체 검사나 루트 회귀를 수행했다고 쓰지 않는다.

첫 원고 `MDE-PHASE10-001.md`의 `pytest 27 passed`는 DOC-PARSER-0의 2026-10-25 과거 기록이다. 전자책 확장판 검사 수치가 아니며 오늘 구현량이나 검사 합계에 더하지 않는다. 첫 원고를 참고하는 목적은 작성 방식과 증거 구분을 확인하는 데 있다.

이번 집필의 검사는 원고의 H2 10개와 필수 표기, 원문 발췌·시그니처 일치, 실습 Python 문법, 허용 파일 범위와 Git 공백 검사로 한정한다. 독자용 실습과 제작기 테스트는 실행하지 않는다. 자동 검사가 통과해도 원고의 편집 품질, 실습 재현, 사용자 실사용·출판 승인은 별도로 남는다.

## 오류와 주의

- **연결 키와 경로:** `STEP-01` 대신 실제 앵커 `chapter-001`을 쓴다. manifest 장 순서가 바뀌면 연결할 장도 다시 확인한다. 보충 `path`는 원고 manifest 폴더 기준이며, 보충 JSON 폴더 기준으로 고치면 엉뚱한 파일을 찾게 된다.
- **입력 형식:** 빈 supplements 목록, 없는 step/path, 알 수 없는 장, 중복 장·파일, 누락·빈 보충 파일, MD가 아닌 파일, 잘못된 JSON·UTF-8은 실패한다. `utf-8-sig`로 BOM을 허용하고 텍스트 읽기의 개행 정규화를 사용한다. 본문을 AI로 교정하거나 문법을 검증하지 않는다.
- **보충 경로의 경계:** `PureWindowsPath`로 드라이브·루트·`..`·콜론을 검사한다. 절대경로, 드라이브 상대경로, UNC, ADS를 거부하고 `resolve()` 후 manifest 루트 밖인 심볼릭 링크·junction 이탈도 차단한다. 이는 파일시스템 링크의 외부 이탈 검사다. 본문 안의 웹 링크를 검사한다는 뜻이 아니며, 기존 `_read_manifest`의 모든 원고 경로에 이 새 제한을 적용했다고 확대 해석하지 않는다.
- **파일 별칭:** `samefile`로 원고·보충 파일의 하드링크 중복을 확인한다. 출력이 입력과 같은 경로나 같은 파일이면 거부하고, 출력 심볼릭 링크와 출력끼리 같은 파일인 경우도 검사한다. 이름만 다르면 안전하다고 가정하지 않는다.
- **기본판 차이:** 확장 모드에서 기존 toc/basic이 예상 UTF-8 바이트와 다르면 오류다. `--overwrite`로 해결하려 하지 말고 원래 manifest·원고와 보호할 기본판이 같은 기준인지 확인한다. 같으면 읽기만 하며 바이트·mtime·inode 보존을 테스트한다.
- **게시의 범위:** `expanded.md`는 같은 출력 폴더의 `.expanded-*.tmp`에 완성한 뒤, 기본값에서는 `os.link`로 배타 게시한다. 게시 순간 다른 작업이 만든 expanded가 있으면 덮어쓰지 않는다. overwrite에서는 `os.replace`로 그 파일을 원자 교체하고, `finally`에서 임시 파일을 정리한다. 기본 게시에는 하드링크를 지원하는 로컬 파일시스템이 필요하다.
- **보장의 한계:** 위 원자성은 확장판 한 파일의 게시·교체 범위다. toc/basic은 없는 파일을 순서대로 직접 쓰므로 세 결과 파일 전체의 트랜잭션은 아니다. 첫 생성의 디스크·권한 오류로 일부 결과가 남을 수 있다. 외부 프로세스가 검사 도중 입력이나 출력·링크를 바꾸는 상황을 방어한다고 보장하지 않는다. 같은 입력·출력 폴더를 동시에 수정하지 않는다.
- **내용과 승인:** 상대 이미지 복사, 본문 링크 재작성, Markdown 문법·앵커 충돌 검사는 하지 않는다. 승인 목록은 사용자 검토를 전제하며 출판 적합성 인증이 아니다. W1의 `allowedFiles`도 프롬프트와 Git 사후 검사로서 OS의 파일별 쓰기 차단 장치가 아니다. ignored 파일·저장소 밖·Git 메타데이터의 모든 변조를 추적한다는 보장은 없다.
